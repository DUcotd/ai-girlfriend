# PRD：小爱好感度系统重构与行为优化

## 项目信息

- **Language**：简体中文
- **Programming Language**：后端 Node.js（ESM，无框架，纯函数规则模块）；前端 Next.js 16 App Router + React 19 + TypeScript strict + Tailwind CSS
- **Project Name**：`ai_girlfriend`
- **原始需求复述**：小爱（情感陪伴型 AI）的**好感度**（0–100 单一数值）是整个应用的核心经济系统，驱动关系阶段、PAD 情绪基准、主动消息日配额三件事。当前系统存在 5 个真实缺陷（阈值多处硬编码、关键词词典两套不一致、疲劳逻辑内联不可测、前端第三份阈值镜像、无自动化回归），且好感度变化**完全不可追溯**。本次目标：**重构 + 行为优化**（结构收敛 + 引入更真实的行为机制），前端一起改，允许重置存档（不写迁移/兼容逻辑）。

## 1. 背景与目标

### 1.1 现状（已核实，来自代码）

好感度驱动三条既有链路，均以 `backend-node/src/core/relationshipStages.js` 为**唯一事实源**：

| 链路 | 消费点 | 现状 |
|---|---|---|
| 关系阶段 | `relationshipStages.js` 5 档：0-15 stranger / 16-34 acquaintance / 35-59 friend / 60-84 close / 85-100 lover，默认 35 | 事实源正确，但下游多处绕过它 |
| PAD 情绪基准 | `EmotionEngine.updateBaselineForAffinity()` | 已按 stage 名挂 `TIER_PAD`，写法正确 |
| 主动消息配额 | `ProactiveEngine` 的 `STAGE_ECONOMY` | 已按 stage 名挂参数，写法正确（可作本次重构的范式参考） |

### 1.2 五个真实缺陷

| # | 位置 | 问题 | 影响 |
|---|---|---|---|
| A | `core/affinityRules.js` | 6 条规则内联硬编码 35 / 60 / 10 / 70 / 80 / 90，未引用 `relationshipStages.js` | 违反「分档逻辑必须引用唯一事实源」约定；改阶段边界会漏改规则 |
| B | `core/EmotionEngine.analyzeInput()` | ① 另硬编码 15/34/59/84 一套阶段边界；② 自带 `intimacyWords/praiseWords/criticismWords/teasingWords` 词典，与 `affinityRules.js` 的 `HARD_REJECTION/SOFT_REJECTION/MILD_INTIMACY/DEEP_INTIMACY` 两套表不一致（如「抱抱/亲亲」一边算重度亲密、一边算普通亲密） | 同一句话在情绪分析和好感度判定里语义打架，手感不可预测 |
| C | `core/AiGirlfriend._finalize()` | 「近 24h 加分疲劳」的裁窗、计数、push 时间戳业务逻辑内联在编排器 | 规则本体与编排耦合，无法单测 |
| D | `frontend/src/components/character/CharacterPanel.tsx` | 第三份阈值镜像 `16/35/60/85`（`getAffinityTitle`），靠人肉与后端同步 | 前后端阶段名可能不一致 |
| E | 测试 | 无任何好感度自动化回归，只有一次性脚本 `backend-node/scripts/verify-affinity.mjs`，不在 `npm test` | 任何规则改动都无护栏 |

### 1.3 为什么现在做

1. **可追溯性是用户信任的底线**：当前用户只知道「涨了 2 点」，不知道是「规则几」改的、被哪一步削过；开发者也无法解释一次涨跌。核心经济系统不可观测 = 无法调试、无法调参、无法取信用户。
2. **三份阈值 + 两套词典正在持续漂移**：缺陷 A/B/D 是结构性债务，每加一条规则就多一处不一致，越晚收敛成本越高。
3. **允许重置存档**：本次可清空 `backend-node/data/state.json`，不需要旧数据迁移/兼容逻辑 —— 这是做**存储结构收敛**（引入可追溯账本）成本最低的窗口期。
4. **行为还不够「真实」**：好感度只升不落、单日可被刷分，与「现实中好感缓慢积累、久不联系会冷却」的产品承诺不符。

### 1.4 目标（3 个正交目标）

- **G1 收敛**：好感度的**阶段阈值**与**关键词词典**全项目各只有一处事实源，前后端不再镜像。
- **G2 可测可溯**：规则判定、疲劳计数、时间衰减均为可独立测试的纯函数；每次好感度变化都能回答「为什么变、被哪些规则改过」。
- **G3 更真实**：引入时间衰减与每日涨分上限，让好感度像现实关系一样「缓慢积累、久疏则冷、不可刷分」。

### 1.5 硬约束（不可违反）

- 好感度仍是 **0–100 单一数值**；`relationshipStages.js` 的 5 档（15/34/59/84）是既定事实源，**不重新设计分档**，只把所有引用收敛到它。
- 不改变「好感度驱动什么」的既有关系（阶段人设 / PAD 基准 / 主动消息配额）。
- 前端 ESLint 零容忍（React 19 Compiler 规则：effect 同步体内禁止 setState、render 期间禁止调非纯函数 `Date.now()` 等）。
- **不引入新依赖**，除非有明确论证。
- 暗色主题为默认。
- UI 遵守「防抽动四条硬规则」：① 有激活态的按钮边框常驻（未激活写 `border-transparent`）；② 会显隐的区域预留固定高度；③ 滚动容器加 `[scrollbar-gutter:stable]`；④ 滑块用 `translate-x` 而非 `left/right`。
- 与现有手感对齐：正向上限 +3、负向下限 -10、默认 35、疲劳 24h 内 1~2 次减半、≥3 次归零。

## 2. 用户故事

- **US1（普通用户）**：作为用户，我希望小爱对我的态度随相处时间**真实变化**（久不联系会变冷、每天不能无限刷分），这样「她」才像一个有情绪的人，而不是一个可被攻略的数值。
- **US2（普通用户）**：作为用户，当好感度变化时，我希望**知道为什么**（「你叫了她老婆，她还不太熟，-1」），这样我才理解该怎么相处，而不是面对一个黑盒数值。
- **US3（普通用户）**：作为用户，我希望**同一句话**在小爱的情绪反应和关系判定里是一致的（我说「抱抱」，她该高兴就高兴、该害羞就害羞，而不是两套逻辑打架），这样她的反应才可信。
- **US4（开发者）**：作为开发者，我希望**改一处阈值/词典就能全项目生效**，且**有自动化测试守护**，这样我重构时不必担心漏改前后端或引入回归。
- **US5（开发者）**：作为开发者，我希望能够**独立测试**「越界惩罚」「加分疲劳」「时间衰减」这些规则，不依赖 LLM、不依赖编排器，这样我能对新机制做参数调优。

## 3. 需求池

> 优先级：**P0 Must have / P1 Should have / P2 Nice to have**。每条含【需求描述】【验收标准（可验证）】【对应现状缺陷编号】。
> `must` = 必须；`should` = 应当；`could` = 可以。

### P0 — 本次必须做

#### P0-a 好感度分档阈值全项目单一事实源

- **需求描述**：`relationshipStages.js` 是唯一的阶段阈值事实源。所有需要「按关系阶段判断」的逻辑，**必须通过 `getStageForAffinity(affinity).stage` 拿到阶段名再比较**，禁止在业务代码里直接写 `affinity < 35`、`affinity <= 84` 这类数字。
  - 具体收敛点：
    - `affinityRules.js`：删除 35 / 60 硬编码，改用阶段名比较。
    - `EmotionEngine.analyzeInput()`：删除 15/34/59/84，改用 `getStageForAffinity(affinity).stage` 分支。
    - 前端 `CharacterPanel.getAffinityTitle()`：删除 `16/35/60/85`，改为消费后端下发的 stage 元数据（见 P0-a-3 / 第 4 节）。
  - 规则自身的**非阶段参数**（如超低好感保护阈值 10、惯性系数等，它们不是阶段边界）不得内联散落，收敛到 `affinityRules.js` 顶部一个具名配置对象 `AFFINITY_RULES`，每项带注释说明取值理由。
- **验收标准**：
  1. 全仓库 grep `affinity < 35 | affinity <= 15 | affinity <= 84 | 16 | 35 | 60 | 85`（在好感度/阶段上下文内）**零命中**硬编码阶段边界（阶段边界只能出现在 `relationshipStages.js`）。
  2. 修改 `RELATIONSHIP_STAGES` 任一 `min/max` 后，规则、情绪、前端展示**同步变化**且无需改动其他文件（有测试覆盖）。
  3. 前端不再存在任何阶段阈值字面量；阶段名/标签来自后端响应。
- **对应现状缺陷**：**A、B（阶段边界部分）、D**

#### P0-b 好感度关键词词典单一事实源

- **需求描述**：新建唯一词典模块（建议 `backend-node/src/core/lexicon.js`），收敛并**去重对齐**现有两套表。`affinityRules.js` 与 `EmotionEngine.analyzeInput()` 均只从此模块取词，不得各自维护词表。
  - **语义对齐原则**：**同一个词在情绪分析和好感度判定里是同一个语义**。据此确定唯一分类与归属（优先级从高到低，命中即归类，避免重复）：
    - `HARD_REJECTION`（真实拒绝）：`不太合适 / 刚认识 / 陌生 / 不熟 / 保持距离 / 后退 / 请不要这样 / 别这样 / 这样不好 / 我们还不熟 / 太突然了`
    - `SOFT_REJECTION`（傲娇/软拒绝）：`讨厌 / 哼 / 走开 / 不理你 / 不跟你说了 / 烦人 / 坏人 / 大坏蛋 / 过分 / 欺负 / 坏蛋 / 不理你了 / 哼唧`
    - `DEEP_INTIMACY`（重度亲密）：`爱你 / 亲亲 / 抱抱 / 么么 / 老婆 / 老公 / 宝贝 / 亲爱的`
    - `MILD_INTIMACY`（轻度亲密）：`喜欢你 / 想你 / 喜欢你呀 / 想你了`
    - 补充情绪向词表（情绪分析专用，与上面四类**互斥**）：`PRAISE`、`CRITICISM`、`TEASING`、`EXCITING`、`CALMING`、`SAD`、`QUESTION`
  - **关键修正**：现有冲突必须消除 —— 「抱抱/亲亲」在两边都归 `DEEP_INTIMACY`；「讨好/喜欢」归 `MILD_INTIMACY`（区别于 `DEEP_INTIMACY` 的「爱你」）；「讨厌」归 `SOFT_REJECTION`（不再同时算 `CRITICISM`）；「哼」归 `SOFT_REJECTION`（不再同时算 `TEASING`）。
- **验收标准**：
  1. 全仓库只有一处定义这些词表；`affinityRules.js` 与 `EmotionEngine.js` 均为 import。
  2. 单测：对任一词（如「抱抱」「讨厌」），在好感度判定与情绪分析两条链路上返回**同一分类**。
  3. 存在「词表无重叠」断言：`HARD_REJECTION ∪ SOFT_REJECTION ∪ DEEP_INTIMACY ∪ MILD_INTIMACY` 两两交集为空，且与情绪向词表交集为空。
- **对应现状缺陷**：**B（词典部分）**

#### P0-c 规则判定与「加分疲劳」解耦并可独立测试

- **需求描述**：
  1. 把「近 24h 加分疲劳」的**裁窗、计数、push 时间戳**从 `AiGirlfriend._finalize()` 抽离为独立纯模块（建议 `core/affinityFatigue.js` 或并入规则模块），暴露纯函数，例如：
     - `pruneGainEvents(events, now, windowMs) -> number[]`（裁窗）
     - `applyGainFatigue(change, recentPositiveCount) -> { change, applied }`（按 24h 计数套用疲劳规则）
     - `recordGain(events, now) -> number[]`（push）
  2. `validateAffinityChange()` 保持为**纯函数**：不读文件、不读时间、不读全局状态；疲劳所需的 `recentPositiveCount` 由调用方注入（现状已如此，需保持并补齐可测试性）。
  3. `_finalize()` 只负责「取当前时间 → 调纯函数 → 写回状态」，业务判断零内联。
- **验收标准**：
  1. `validateAffinityChange`、`applyGainFatigue`、`pruneGainEvents` 均为无副作用纯函数，可在无 LLM、无文件系统下直接调用。
  2. 单测覆盖边界：24h 内 0 次 / 1 次 / 2 次 / 3 次正增长，以及第 24h 边界裁窗。
  3. `_finalize()` 中不再出现 `24 * 60 * 60 * 1000`、`filter(t => now - t < ...)`、`push(now)` 这类规则逻辑（只允许保留对模块的单次调用）。
- **对应现状缺陷**：**C**

#### P0-d 好感度变化可追溯（可观测性）

- **需求描述**：系统必须能回答「**这次为什么涨/跌了几点、被哪些规则改过**」。
  1. `validateAffinityChange()` 的返回值由「单个 number」升级为可追溯结果对象，建议：
     ```
     { change: number, trace: Array<{ rule: string, from: number, to: number, reason: string }> }
     ```
     每命中一条规则（硬拒绝 / 软拒绝 / 越界惩罚 / 加分疲劳 / 超低保护 / 高好感惯性 / 日上限截断）就往 `trace` 追加一条「修正前后值 + 人话原因」。
  2. 引入**好感度变更账本（affinity ledger）**，每次变动追加一条记录（建议持久化到 `state.json` 或独立文件 `affinity_ledger.json`）：
     ```
     { at: ISO, before, after, rawChange, finalChange, stage, userInputDigest, trace }
     ```
     - 账本**上限 200 条**（超出丢弃最旧），避免状态文件无限膨胀。
  3. 后端通过 API 暴露账本与最近一次变更原因（如 `GET /api/affinity/history`、随 chat 响应返回 `affinityTrace`），供前端展示。
- **验收标准**：
  1. 任一好感度变化都能取到 `trace`，且 `trace` 中每条修正的 `from → to` 累加可复现 `finalChange`（有测试断言 `rawChange` 经 trace 逐步修正后等于 `finalChange`）。
  2. 账本写入后可通过 API 读取；重启后不丢失；超过 200 条自动裁剪。
  3. chat / chatStream 的响应体包含 `affinityTrace`（可为空数组）。
- **对应现状缺陷**：**E（的一半，回归测试见 P1-d）**

### P1 — 本次建议做

#### P1-a 时间衰减（长期不聊，好感度自然回落）

- **需求描述**：好感度因「长期无用户互动」而自然回落，模拟「久疏则冷」。
- **产品化参数与边界（可落地的具体数字）**：

  | 参数 | 取值 | 理由 |
  |---|---|---|
  | **启动阈值**（多久不聊开始衰减） | 距最后一次**用户消息**满 **72 小时**后启动 | < 48h 会误伤「周末/出差两天没聊」的正常用户；> 5 天则几乎无感。72h（3 天）是「明显疏远」的心理节点 |
  | **衰减速率（stranger / acquaintance / friend）** | 每满 **24h** 减 **1 点** | 正向单次最多 +3、且受日上限约束；1 点/天是「温和冷却」而非「惩罚」，一个月≈ -30，可见但不致命 |
  | **衰减速率（close / lover）** | 每满 **48h** 减 **1 点** | 关系越亲密、情感黏性越强，冷却更慢，符合「感情经得起短暂分离」的直觉 |
  | **止损下限** | **不低于当前阶段的下沿**（stranger→0, acquaintance→16, friend→35, close→60, lover→85） | 防止「仅因不活跃」把关系**降档**造成挫败；衰减只在本阶段内进行 |
  | **打断方式** | 用户发任意一条消息即刷新「最后互动时间」为当前时刻，重新开始 72h 计时；**已发生的衰减不返还** | 一次互动即算「和好信号」；不返还避免「先冷后打卡来回横跳刷分」 |
  | **阶段相关差异** | 见上两行（低阶段快、高阶段慢） | 陌生人本就无羁绊、易遗忘；挚友/恋人感情韧性强 |

  - **落地方式**：惰性计算 —— 不新增定时器。在每次 `_prepare()` 或读取状态时，用 `(now - lastUserActiveTime)` 与上次结算时间戳推算应扣点数（按整天取整），一次性结算并写入账本（`trace` 记 `rule: 'time_decay'`）。`lastUserActiveTime` 复用 `ProactiveEngine` 已有的用户活跃时间语义（同一状态或对齐口径）。
- **验收标准**：
  1. 构造「最后一句话在 T-72h」→ 触发衰减；「T-71h」→ 不衰减（边界测试）。
  2. friend 阶段好感度 40，静默 5 天 → 降至 35 后**停止**（不跌破阶段下沿）。
  3. close 阶段每 48h 才 -1（速率测试）。
  4. 衰减期间用户发消息，计时重置，72h 内不再衰减。
  5. 每次衰减在 `trace` 记 `time_decay`，账本可查。
  6. 衰减不引入后台定时器（代码审查确认）。
- **对应现状缺陷**：**新增行为（G3）**，与 E（需纳入回归）相关

#### P1-b 每日涨分上限（防刷分）

- **需求描述**：单个自然日内好感度**正增长总量**封顶，超出部分**截断**（不清零整天）。
- **产品化参数与边界**：

  | 参数 | 取值 | 理由 |
  |---|---|---|
  | **每日正增长上限** | **+8 点 / 自然日** | 正常使用一天涨 3~6 点（受单次 +3 与疲劳限制），+8 略高于正常峰值，仅在异常刷分时生效 |
  | **计数窗口** | **本地自然日**，00:00 重置（复用 `ProactiveEngine.dayKey()` 的口径） | 与主动消息每日配额「同一天重置」语义一致，用户心智统一 |
  | **超额处理** | **截断**：当剩余额度 `R = 8 - 今日已涨`，则本次正向变化取 `min(change, R)`；`R ≤ 0` 时正向变化归 **0** | 比「整日清零」公平，避免「最后一句把一整天努力清零」的挫败感 |
  | **与其他规则叠加顺序** | 先「单次上限/越界惩罚/疲劳」→ 最后「日上限截断」 | 日上限是全局总量闸门，必须最后生效，才能正确反映「今天还剩多少额度」 |

- **验收标准**：
  1. 同一自然日内累计正增长到 8 后，后续正变化被截为 0（不翻滚到负）。
  2. 第 7 点额度时来一个 +3 → 只涨 +1（截断测试）。
  3. 跨过本地 00:00 后额度重置为 8。
  4. 日上限截断在 `trace` 记 `daily_cap`。
- **对应现状缺陷**：**新增行为（G3）**

#### P1-c 既有规则按阶段更精细

- **需求描述**：把现有按「数字」判断的规则改为按「阶段」表达，并适度细化。
- **产品化参数与边界**：

  1. **越界惩罚**（用户说了超越当前阶段的亲密话）—— 按阶段分级：

     | 阶段 | 轻度亲密（MILD）越界 | 重度亲密（DEEP）越界 |
     |---|---|---|
     | stranger | **-2** | **-3** |
     | acquaintance | **-2** | **-3** |
     | friend | **0**（不罚，可正常加分） | **-2** |
     | close / lover | 0（欢迎） | 0（欢迎） |

     理由：关系越浅、越界越冒犯（延续现有产品语言）；friend 阶段「喜欢你」属自然表达不再惩罚，仅「老婆/索吻」这类恋人言行 +快速的仍扣分。

  2. **软拒绝 / 傲娇**：保持现有语义 —— 在 `close / lover` 阶段且伴随亲密 → 视为**傲娇调情**（不阻断、不扣分）；否则阻断正向变化（归 0）。**改为按 stage 名比较**，不再引用数字。

  3. **高好感惯性**（对负变化的衰减）—— 按阶段收敛为三档，**取消现有 70/80/90 三档数字**：

     | 阶段 | 负变化系数 |
     |---|---|
     | friend 及以下 | ×1.0（不衰减） |
     | close | **×0.5** |
     | lover | **×0.2** |

     理由：只保留与阶段一一对应的档位，避免新增 70/80/90 这类「游离于事实源之外的魔法数」；深爱难以骤降的手感由 lover ×0.2 保留。

  4. **超低好感保护**：保留 `affinity < 10 时正向 ×0.3`，作为 `AFFINITY_RULES` 中的**具名规则参数**（非阶段边界，注明理由：心灰意冷时一两句好话挽回有限）。

- **验收标准**：
  1. 越界惩罚在五个阶段的分档表逐条测试通过。
  2. 软拒绝在 `close/lover + 亲密` 时不阻断、在低阶段时阻断。
  3. 惯性系数：friend 不衰减、close ×0.5、lover ×0.2 各一条测试。
  4. 规则代码中不再出现 70/80/90 等惯性数字（只有具名的阶段档位）。
- **对应现状缺陷**：**A（规则阈值）**

#### P1-d 好感度规则自动化回归进入 `npm test`

- **需求描述**：把一次性脚本 `verify-affinity.mjs` 的场景**收编**为正式测试，纳入 `npm test`；新增 P1-a/b/c 新机制的用例，让现有 `npm test`（当前仅 `test-stream-filter.mjs`）串起全部规则测试。
- **验收标准**：
  1. `npm test` 一条命令跑通好感度全部规则用例（阶段映射 / 越界 / 疲劳 / 正向 & 负向上限 / 惯性 / 时间衰减 / 日上限 / trace 一致性）。
  2. 任一规则改坏导致测试失败时 CI/本地立即可见。
  3. 删除或降级 `verify-affinity.mjs` 的一次性定位（并入测试目录），避免「两份事实」。

## 4. 前端交互与展示要求

1. **阶段信息来自后端，前端零阈值**（落实 P0-a）：
   - 后端在 `/state` 与 chat/chatStream 响应中下发阶段元数据，建议字段：`stage`、`stageLabel`（中文标签）、`stageShortLabel`、`nextStage`、`pointsToNextStage`、`stageProgress`（当前阶段内 0–1 进度）。
   - 前端 `CharacterPanel.getAffinityTitle()` 直接展示 `stageLabel`，**删除**本地 `16/35/60/85` 镜像。
   - 现有 `AffinityHearts`（每 20 点点亮一颗心）不涉及阶段语义，**保留**，作为纯视觉元素。
2. **好感度面板**：
   - 展示：好感度数值 `x/100` + 进度条（现已有）+ 阶段中文标签（如「朋友」）+ **距下一阶段还差 N 点**。
   - 阶段进度以「当前阶段 min→max」为进度条基准，给用户「离升级还有多远」的确定感。
3. **好感度变化可解释**（落实 P0-d）：
   - 每次好感度变化后，在面板给出**一句人话原因**（取 `affinityTrace` 最后一条命中规则的 `reason`，如「你叫了她『老婆』，还不太熟，-1」）。
   - 变化数字用颜色区分：正增长绿色、负变化红色、归 0 中性；数值切换用 `translate-x`/透明度过渡，**禁止 `left/right` 布局动画**。
4. **衰减与上限的可见性**：
   - 处于衰减中时，面板提示「似乎有点疏远了…」（不显示具体点数，避免机械化）。
   - 触及每日涨分上限时，可提示「今天她好像有点…处够多了」，暗示额度用尽。
5. **遵守既有 UI 硬规则**：所有新增/改动的可显隐区域**预留固定高度**（防止布局抽动）；任何会有激活态的按钮边框**常驻**（未激活 `border-transparent`）；滚动容器加 `[scrollbar-gutter:stable]`。
6. **React 19 / ESLint 合规**：不使用 render 期间的 `Date.now()`（阶段进度、衰减提示等服务端/派生量由后端下发或 `useEffect` 内计算并落 state）；不在 effect 同步体内直接 setState。

## 5. 非功能需求

- **性能**：`validateAffinityChange` 及全部规则纯函数须为 O(词表大小) 的常数级计算，不得引入 I/O 或异步。前端渲染不得因好感度更新产生布局抖动（见防抽动硬规则）。
- **可测试性**：所有规则、疲劳、衰减逻辑均为**无副作用纯函数**，且不依赖 LLM、不依赖文件系统、不依赖真实时钟（时间通过参数注入）。测试纳入 `npm test`，退出码非零即失败。
- **可观测性**：每次好感度变化产出结构化 `trace` + 账本记录（`at / before / after / rawChange / finalChange / stage / trace`），账本上限 200 条，可通过 API 读取；日志对每条规则命中保留「修正前 → 修正后」的可读输出。
- **可维护性**：阶段阈值唯一事实源（`relationshipStages.js`）、关键词唯一事实源（`lexicon.js`）、规则参数集中具名（`AFFINITY_RULES`）；新增一条规则或改一个阈值只需改一处。
- **兼容性**：允许重置 `data/state.json`，**不保证**旧存档兼容；不需要迁移脚本。
- **依赖**：不新增第三方依赖；复用现有 `jsonStore`、`dayKey` 口径。
